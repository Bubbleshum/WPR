a more careful Vulkan renderer for every phone, and reports that finally say which graphics chip
a problem happened on.**

### Graphics on Mali and PowerVR phones (OpenGL)

Games' shaders were written for Direct3D, which always calculates at full precision. On OpenGL,
WPR was asking the phone for "medium" precision in the part of a shader that colours each pixel.
Adreno chips (Snapdragon phones) quietly use full precision anyway, so nothing showed there. Mali
and PowerVR chips really do use half precision, which is too coarse for lighting, fog and for
finding the right spot in a large texture. WPR now asks for full precision wherever the phone
offers it.

WPR also changed how it hands each object's geometry to the graphics chip on OpenGL. Windows Phone 8
games send theirs a little at a time, thousands of times a frame, and WPR was adding each piece to
one large shared buffer, which OpenGL drivers on phones handle badly: they stop and tidy up after
every piece. Each piece now gets a small buffer of its own. Measured on a Galaxy S24 on OpenGL, the
time WPR spends drawing a frame fell from 25-36 ms to about 3.5 ms in an Asphalt 7 race, and from
16-25 ms to about 3 ms in Modern Combat 4, which now runs at a steady 60 frames a second there
instead of about 40. That is close to what the same phone does on Vulkan.

WPR now also keeps each game's compiled shaders on the phone when it runs on OpenGL, as it already
did on Vulkan. The first launch of a game builds them as before; later launches load them back
instead. On a Snapdragon phone this saves very little, because its driver builds shaders quickly;
it is there for Mali and PowerVR phones, where building shaders is known to be slow.

If you play on OpenGL on a Mali or PowerVR phone, banding, shimmering textures, wrong lighting and
slow Windows Phone 8 games (Asphalt 7, Modern Combat 4, N.O.V.A. 3) are the things this should
improve. The speed figures above are from a Snapdragon phone. It has not been tested on a Mali phone, as there is not one to
test on, so reports either way are very welcome.

### Texture memory on Mali and PowerVR phones

Windows Phone games ship most of their pictures in a compressed format (DXT). PC graphics chips
understand it, and so do recent Adreno chips (Snapdragon phones), which use it as it is. Mali and
PowerVR chips do not. On those phones WPR unpacked every such texture to full colour when a game
loaded it, which takes four to eight times the memory, and on a phone that is the phone's own
memory. WPR now repacks them into ETC2, a compressed format those chips do understand, on both
OpenGL and Vulkan. Phones that understand DXT are unchanged.

Measured on a Galaxy S24 told to behave as a phone without DXT: graphics memory fell by 23 MB at
Mirror's Edge's title screen and 25 MB at Temple Run 2's on OpenGL, and by 16 MB in each on Vulkan,
with no visible difference in the picture. The saving grows with the game: it is a quarter to an
eighth of whatever its compressed textures took before. On a phone with 3 or 4 GB of memory this
can be the difference between a large game staying open and being closed by Android.

The repacked textures are kept in the game's folder, so the work is done the first time a game
shows each texture and not again. The first launch of a game after this update loads a little
slower than later ones.

Repacking is a second round of compression, so a texture can lose a little detail. If a game looks
worse to you than it did, please send a **Play with logging** report and say what looks wrong. It
has not been run on a real Mali or PowerVR phone, as there is not one to test on.

### Vulkan, on every phone

WPR's Vulkan renderer was checked with Khronos's own validation tools, which watch every graphics
call for mistakes that a forgiving driver hides and a strict one need not. They found five, all
fixed:

- **Three in how a finished frame is put on the screen.** WPR could reuse a signal for the next
  frame while the last one was still using it, could copy the picture to the screen before the
  screen's buffer was confirmed ready, and shared one "frame finished" signal between all of the
  screen's buffers. Each buffer now has its own, and each step waits for the one before it.
- **One when a game changes the same texture twice in one frame**: the two changes are now put in
  order.
- **One in Windows Phone 8 games**: a flat texture could be handed to a shader that expects a
  six-sided one (Temple Run 2 and Temple Run: Oz did this on every frame). The shader now gets an
  empty six-sided texture, which is what Direct3D gave it.

On the phones tested these changes make no visible difference, because their drivers tolerated the
mistakes. They are the kind of mistake that can show up as flicker, a black screen or a crash on a
stricter driver.

### Reports say which graphics chip

Every crash report and logging run sent to WPR Hub now includes the phone's graphics chip, its
driver version, and what that driver supports. Until now a report said only "Vulkan" or "OpenGL",
so a problem that only happens on one family of phones looked the same as any other. If a game
misbehaves for you, a **Play with logging** run is now much more useful than before.

### Grand Theft Auto: San Andreas

A crash just after starting a new game was reported on a Mali phone. It turned out not to be the
graphics chip: it happens on any device when version **1.0.0.0** of the game is used with game data
made for **1.0.0.2**. Install the 1.0.0.2 package and the same data plays.

> **Upgrading.** Install the new APK over the top on Android, or run the installer on Windows. Your
> games, saves and sign-in stay put. Nothing needs reinstalling.
