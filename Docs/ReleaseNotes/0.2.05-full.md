### The crash

Reported through a logging run from a realme RMX3938 (Android 16, Mali-G57 graphics) on OpenGL. The
game closed about five seconds after starting, with only "the game process exited unexpectedly":

```
E libEGL  : call to OpenGL ES API with no current context (logged once per thread)
F libc    : Fatal signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x18 in tid 14931 (Thread-3)
      #00 pc …  libc.so (__memcpy_aarch64_simd+80)
      #01 pc …  libFNA3D.so (MOJOSHADER_effectCommitChanges+768)
```

**What it was.** Plants vs. Zombies loads its images on a background thread, and premultiplies each
one by drawing it into a render target with a `SpriteBatch`. It does that under its own lock,
`ResourceManager.DrawLocker`, which the game's `Draw` also takes. So two threads draw, but never at
the same time.

That is fine on Direct3D 11 and on Vulkan, which accept drawing from any thread. It is not fine on
OpenGL, where a context belongs to one thread. FNA3D's OpenGL driver knows this for *resource* calls
(creating and filling textures, buffers and effects): from any other thread it either queues them
for the device thread or, on Android since 0.2.03, runs them on a worker context of its own. It does
nothing of the kind for *drawing* calls: setting a render target, clearing, applying an effect, the
draws themselves and the render-state setters all run on whichever thread calls them. On the loading
thread there is no GL context at all, which is the `libEGL` line, and MojoShader keeps its GL context
pointer **per thread**, so it was null there. Applying an effect then copied shader parameters into
the register file of a null context, address `0x18`, and the process died.

Before 0.2.03 the same game didn't get that far on OpenGL: it hung on its PopCap logo, because its
loading thread waited for a texture to be created, and that only happened at the next frame, which
the game couldn't draw while the loading thread held its lock. The 0.2.03 worker contexts let the
textures through, which moved the failure on to the first draw.

**The fix has two halves.**

1. **Drawing from another thread is run on the device thread.** On OpenGL only, every drawing call
   made off the device thread is handed to the device thread and the caller waits for it, so the
   calls still run in the order the game made them and see the state it set. Direct3D 11 and Vulkan
   never take this path.
2. **The device thread keeps working while it waits for the game's lock.** Handing calls over is not
   enough on its own: the loading thread waits for the device thread while holding `DrawLocker`, and
   the device thread is stuck in `Draw` waiting for `DrawLocker`. So the patcher now sends every
   `lock` in game code (`Monitor.Enter`) to a WPR version that, on the device thread with OpenGL,
   retries the lock every millisecond and runs any calls waiting for it in between. Anywhere else it
   is the ordinary `Monitor.Enter`. This also covers the case from 0.2.03 where a game's main thread
   waits on its loading thread, without depending on the worker contexts.

One detail mattered for the picture rather than the crash. Uploading vertex data from the loading
thread on a worker context and then drawing with it on the device context drew the *previous*
sprite's vertices. The device context already had `SpriteBatch`'s shared vertex buffer bound, and
OpenGL only guarantees another context's writes are seen after binding again. Plants vs. Zombies'
title background came out shrunk into one corner. Vertex and index uploads from a background thread
now go to the device thread too. Creating textures stays on the worker contexts, since a new
texture can't already be bound.

**Tested on:**

| | |

| Windows, Direct3D 11 | ✅ title and menu (reference) |
| Windows, OpenGL | ✅ title → menu → level 1-1 (froze on the logo before) |

The Treasures of Montezuma, which also loads in the background, still plays on OpenGL on the
emulator.

This is a patcher change (version 40). Installed games are repatched automatically the next time
they're started, on both Windows and Android. Nothing needs reinstalling.

### Known issues

- **Not yet tested on a Mali phone.** The fix was tested on OpenGL on the Android emulator and on
  Windows, not on the realme phone that reported it.
- **Plants vs. Zombies still freezes on Windows if you force Vulkan.** WPR's Windows copy of the
  graphics library is missing a Vulkan fix the Android one has, and it can't be rebuilt here yet.
  Windows uses Direct3D unless you force something else, and that plays.

> **Upgrading is normal.** Install the new APK over the top on Android, or run the installer on
> Windows. Your games, saves and sign-in stay put. Your installed games are updated automatically
> the first time you start them, which takes a moment longer than usual.
