**Cut the Rope plays**, and four more games that used to show an error instead of starting now
run — **Cut the Rope: Experiments**, **Little Acorns**, **Rabbids Go Phone** and **Flight Control
Rocket**, three of which get into actual gameplay. None of them was ever really broken; they are
built a way WPR had no support for at all. Ten games in the library have that shape: five now run,
a sixth puts its opening screen on the display for the first time, and the last four each stop
somewhere of their own.

**Half of those ten are landscape games**, and every one of them was being squeezed into an
upright screen until now.

**Funny Bounce no longer goes blank when a game ends**, and the cause of that turned out to affect
saved data in several other games on Android.

**The Treasures of Montezuma plays**, after an error that turned out to be WPR's own patching
setting off the game's copy protection.

**Plants vs. Zombies plays on Android.** It used to sit on the PopCap logo for ever; the cause was
in the graphics driver, and it could catch any game that draws from two places at once.

**Links in games open now** — in your browser, or in the right app. Cut the Rope's cartoons open in
YouTube, and its Share button brings up the phone's share menu.

**Android now needs Android 7.0 or newer**, because WPR runs on a different .NET engine there
than it used to. That single change fixed a whole family of games that used to close on startup
with an error about invalid code — **iStunt 2** is the one to try first.

### Five games that were never really broken

A Windows Phone game is usually one of two things: it either draws every frame itself and owns the
screen, or it is built out of buttons and pages like an ordinary phone app. WPR runs the first
kind; the second is a much larger job, still not done.

There is a third shape, which Microsoft encouraged — an ordinary app on the outside, with a page
and the normal app lifecycle, but the page is empty and the game draws every frame inside it. It
was the natural way to build a game that wanted a proper phone menu, a web view for signing in, or
the phone's own video player. From the outside these look exactly like the second kind, so WPR
turned them away without looking inside. Look inside **Cut the Rope** and the page is empty; its
developer left a comment saying so:

> *No XAML content is required as the page is rendered entirely with the XNA Framework*

WPR now recognises the shape and runs the game underneath the page. **Cut the Rope was played end
to end** on Windows and Android — menu, box shelf, level grid, and a level finished with three
stars. **Cut the Rope: Experiments** plays too — Play, the box shelf, and into a level.

**Rabbids Go Phone** plays — main menu, then **My Rabbid** and into the room with your Rabbid in
it. **Little Acorns** plays a level, and **Flight Control Rocket** gets into one.

### A menu where no button did anything

**Cut the Rope: Experiments** drew its menu, took your taps and did nothing with any of them —
Play, Album and Options alike. It looked for all the world like the taps were not arriving.

They were. The tap reached the right pixel, the game read it, and the game's own code worked out
which button you had pressed. What it could not do was *run* the method that handles the press —
one branch of it, the one that would have opened the Marketplace page to sell you the full game,
referred to a piece of Windows Phone WPR had never built. A method that mentions something missing
cannot be run at all, even down a branch you never take, so the first press of any button failed
before it did anything.

One property later, all three buttons work and the game plays.

That shape is worth knowing, because it is the opposite of what it looks like: **a menu where
nothing responds, and no error on screen, is usually one missing piece inside the button handler
rather than anything to do with touch.**

### Half of them are landscape, and were being handed a portrait screen

Five of these ten games are played with the phone on its side — and WPR was giving every one of
them the upright screen. A game that lays its menu out across the full width then had barely half
of it to draw into, and the rest fell off the edge.

**Little Acorns** and **Flight Control Rocket** were the visible cases: the title ran off both
sides and a whole column of buttons was cut away. Both are now the right way round — Little Acorns
shows its complete menu, and Flight Control Rocket gets past its menu into an actual level.

The page itself says which way round it wants to be, and WPR now asks it rather than assuming. It
asks the *running* page rather than reading the file, which matters more than it sounds: Little
Acorns' page is written down as upright and switches itself to landscape as it starts, so anything
reading the file alone would still have got it wrong.

### A black screen that was a missing picture

Rabbids Go Phone's main menu drew its logo and all five options perfectly — on a flat black
background. The background was supposed to be a hand-drawn blue city, and it is not part of the
game's own drawing at all: it is a picture placed on the app page behind it, which WPR was not
painting.

Games of this shape hand WPR a page of phone controls and ask for a picture of it back, to draw
into their own scene. Until now WPR handed back an empty picture — deliberately empty rather than
blank-white, so the game stayed visible and only the controls were missing. It now actually paints
that page: backgrounds, panels, borders, shapes and images, including images stored inside the
game rather than as a file on disk, which is where this one lived.

**Text is not painted yet.** That needs a whole type renderer and is its own piece of work, so a
page whose content is words still comes out empty. Gradients and rotated elements are likewise not
drawn. Everything WPR meets and cannot paint is now named once in the log, so a blank patch has a
reason rather than being indistinguishable from a fault.

**Sid Meier's Pirates!** gets the other half of this: its opening screen is nothing *but* those
controls, so it showed nothing at all. It now displays its 2K Games logo page. Beyond that it
needs the text renderer like everything else.

### The same shape again, one game later

Rabbids Go Phone's **My Rabbid** — the main thing the game is for — took your tap and sat there.
Exactly the pattern above, for exactly the same underlying reason.

The screen it opens builds a progress spinner while it loads, using a standard Windows Phone
control that WPR had never needed before. A piece of code that mentions something missing cannot
be run *at all*, so the whole of that screen's setup failed before it had done anything, the
screen was never added, and the menu simply stayed where it was. Nothing on screen said so.

The control now exists and the game plays. The same control appears on two more of its screens, so
this was not one screen's problem.

Fixing it turned up a second one underneath: the list of things on a phone page was missing the
base type Windows Phone gives it, so the ordinary act of adding a control to a page had nowhere to
land. That affected every Silverlight game in principle, not just this one.

### The other four

**Big Buck Hunter Pro**, **Carcassonne**, **Galactic Reign** and **The Game of Life** each stop
somewhere else entirely — a phone control toolkit that wants a user-interface thread before one
exists, a resource file that will not resolve, an opening screen that is an ordinary phone page in
its own right, and a fault inside the game's own screen manager. Each also has its own further
gaps behind that (the camera, the maps control, list data-binding), so none is one fix away.

### The cutscenes are skipped

**Cut the Rope**'s opening and closing animations are in a video format WPR has no decoder for —
the phone had one built in. Rather than fail the request and leave the game waiting forever, WPR
accepts it and immediately reports the video as finished, so the cutscene is skipped and play
continues. WPR already converts game music at install time and the same could be done for these;
that is its own piece of work.

The **Cartoons** section is a different thing, and does work — see *Links in games open now*
below.

### A game that could not read its own words

**The Treasures of Montezuma** put an error on the screen and closed, on the phone and on Windows
alike, without ever drawing a frame. The error quoted a negative number, which is the shape of the
problem in one line: the game was looking for something at a position that cannot exist.

To make itself harder to pick apart, the game keeps all of its text scrambled together in a single
block, and works out where any one piece of text sits in that block from a number describing how
the game's own parts are arranged inside its file. It recalculates that arrangement every time it
needs a word — a sound way to notice that somebody has been editing you.

Somebody had. WPR rewrites every game as it installs it, because that is what makes a Windows
Phone game run anywhere else, and a side effect of that rewriting is to renumber the very
arrangement the game was measuring. Nothing about the game actually changed — the parts are all
still there, doing the same things — but their labels did, so the first word the game asked for
sent it to a nonsensical position and it gave up there.

WPR now hands a game back the numbers its original file had, so the arrangement it measures is the
one it was built with and its text unscrambles. **A game that never asks about its own layout
never notices any of this**, which is nearly all of them: across the whole library exactly one
other game is built and protected the same way — **Farm Frenzy 2** — and it is worth another try.

That got it as far as setting up the display, where it stopped again for a quite different reason.
Windows Phone never allowed a game to bring its own visual effects; the phone had a small fixed
set built in and that was the whole choice. So a game asking for one did not hand over an effect —
it handed over a short note naming which of the built-in ones it wanted. WPR took the note at face
value, found it far too small to be an effect, and refused it. It now recognises a request for a
built-in effect as what it is and supplies the real thing.

With both out of the way the game plays: menu, a new game, and a level with the clock running.

### Funny Bounce went blue after every game over — on Android only

The game played fine, and the moment a run ended the screen turned one flat colour and stayed
there. Not a graphics fault: that colour is the background the game paints before drawing anything
else, and nothing was being drawn on top of it.

The game keeps its high scores in a folder and looked in that folder using a Windows-style
backslash. On Windows that means "inside this folder"; on Android it is just part of a filename,
so the game found nothing. Its game-over screen then tried to read the top score out of an empty
list, gave up partway through building itself, and everything it should have drawn after that was
missing — leaving the background.

WPR already translated those separators for reading and writing files, but not for the calls that
list, check or delete them. It does now, which is what the repatch above applies.

**This was never one game's problem.** Four other games in the library store saves or high scores
the same way — **Big Buck Hunter Pro**, **Civilization Revolution**, **Cro-Mag Rally** and **Skulls
of the Shogun**. If a game has ever lost your progress or shown an empty high-score table on
Android, it is worth another try. Windows was never affected, because there a backslash is exactly
what the game meant.

### A game that ran perfectly and never saw a tap — on Android only

**Cut the Rope**'s menu appeared on Android exactly as it should, animating at full speed, and
ignored every tap — which were arriving, in the right place, to the pixel, and being read.

A tap has a beginning, a middle and an end, and a menu button watches for the beginning. WPR was
running the part of the game that watches for taps at half the rate of the part that collects
them, so the beginning of every tap was thrown away before the game next looked; what it saw was a
finger that had already been down a while. No beginning, so no button press, ever. The two now run
in step. Windows was never affected — and this is the second release running in which this symptom
has appeared with a different cause behind it.

### Textures on the older graphics mode

Android normally uses the newer graphics mode. Some phones end up on the older one instead —
either because you picked it under settings → graphics, or because WPR moved you there after the
newer one failed to start a game. Two things were wrong on that path, and both could take a game
down rather than merely look wrong — and a third, found alongside them, turned out not to be about
phones at all:

- **Several 16-bit texture formats could not be uploaded at all.** A game using one drew nothing,
  or the game process died outright. WPR now stores those textures in a format the phone does
  accept and converts on the way in and out, so the game still sees the format it asked for and
  gets its own pixels back unchanged.
- **Reading a texture back was unsafe.** Games sometimes read a picture back out of the graphics
  card — to inspect it, to save it, to build something else from it. Depending on which route a
  game took, that either did nothing at all, closed the game where it stood, or wrote more than it
  had been given room for, which is worse for being invisible: it damages something unrelated and
  the game fails later, somewhere that looks nothing like the cause. WPR now asks whether the
  phone can answer before asking it to, and where it cannot, the game is told the picture is blank
  instead of being closed. **15 of the 38 games tested here read textures back**, including
  **Mirror's Edge**, **Kinectimals**, **Need for Speed: Undercover** and **Skulls of the Shogun**.

**One of these was not Android-specific, and it is the one most likely to have affected you.** A
leftover experimental line was quietly discarding every upload of one texture format, on Windows
and Android alike — any game using it had blank textures everywhere, on every graphics mode, and
nothing said so. WPR announced a picture of one size, handed over one half that size, the handover
was refused for not adding up, and the game drew the empty result faithfully. It looked exactly
like a game that had chosen to draw nothing there.

That is fixed, and with it the 16-bit colour handling is now verified identical across all four
graphics modes. **If a game has ever looked like it was missing artwork** — a blank panel, a
button with no icon, text that never appeared — it is worth another look. Whether a particular
game used that format is not something you can tell by looking, so there is no list to give.

It also closed an old open question. The red-and-blue colour fix in 0.1.05 could never be
confirmed at the time, because the test picture was in exactly this format and came out blank
whatever was done to it. With the blankness gone, that fix is now measured correct rather than
assumed.

**Only the older graphics mode is affected by the first two**; the third was affecting everything.
The default phone mode and Windows are otherwise untouched — measured before and after, they
produce identical results down to the numbers. Needs nothing beyond installing this release: no
repatch and no reinstall over and above what the top of these notes already asks for.

### What prompted the texture work, and what it does not promise

It came out of a report of **Asphalt 5** misbehaving on one particular phone — cars drawn with
pieces missing, and a race that never finished loading — on a graphics chip nobody here has, on
the older graphics mode.

**These fixes are not confirmed to be that game's problem.** They are real faults found while
looking, and two of the three were affecting every game rather than one, so they were worth fixing
on their own account. Whether they are what that phone was seeing is still open, and Asphalt 5 is
not being claimed as fixed in this release.

### Smaller things that came out of it

Pieces of Windows Phone that WPR had never built, none specific to the ten games above. All were
fatal rather than cosmetic — a game that touched one stopped there:

- **The ad banner used a theme value of the wrong kind**, and any game showing Microsoft's advert
  banner failed on the very first frame, before its own code ran at all. This is what stopped
  Funny Bounce starting once the blue screen was out of the way.
- **Positioning something by hand on a page.** WPR's description of how to do it did not match the
  phone's, so a game placing anything at an exact position failed at that moment.
- **Reading an image file** into something a game can draw. A game using it stopped at its first
  picture.
- **Hiding the status bar.** Practically every Windows Phone game asks for this, and WPR had
  nothing to answer with, which broke the page before the game started.
- **Being told the app has started.** There are two ways a game can ask; WPR had one. A game using
  the other never did its first-run setup.
- **Asking how big the screen is, the app way.** WPR answered zero, so any game sizing its layout
  from that was working from nothing.
- **A plain message box**, and the back button at whole-app level rather than per page.

### A different engine on Android, and the games it brings with it

Some games closed the moment they started, with an error saying their code was invalid. The code
was fine — every one of them runs on Windows, and has all along. The engine that ran them on
Android simply refused to accept certain shapes of code, and the shapes it refused are ones that
games hidden behind copy protection produce constantly. It was never a handful of games: more
than five thousand places across the library are built that way.

WPR had been working around it by rewriting the offending code during installation, which fixed
some games and broke others, and shipped three times without ever really settling.

Android builds now use a different .NET engine — the same family that WPR has always used on
Windows — which accepts that code as written. No rewriting, no workaround, and the whole class of
"invalid code" failures is gone. **iStunt 2** is the clearest example: it never got past its
loading screen on a phone and now plays.

**The cost is that Android 7.0 is now the minimum**, up from Android 5.0. The new engine is not
offered for anything older. If you are on Android 5 or 6, stay on 0.1.05 — it will keep working, it
simply will not get newer releases. Phones from roughly 2016 onwards are unaffected.

A 64-bit device is also needed, but that has been true since well before this release — nothing
changed there, and it is only worth mentioning so it is not mistaken for something 0.1.06 did.

Nothing changed on Windows: it is the same Windows 10 version 1809 or newer, 64-bit, as before.

### The back button had started closing games

Pressing back in a game closed it and showed *the game process exited unexpectedly* — an error
about a crash that had not happened.

Android changed the rules underneath us. From Android 16, an app built against the newest system
version gets the modern "swipe back" behaviour automatically, and the price of it is that the old
way of being told about the back button stops working. WPR uses the old way, deliberately: on
Windows Phone, back is something the **game** handles — it walks you back through the game's own
screens and only leaves at the top. With the notification gone, Android simply closed the game
itself, and WPR read that sudden ending as a crash.

Back is now delivered to games again, so it does what it did on the phone. Holding it still
force-quits a game that ignores it.

This one was easy to miss, because it only showed up on games that **ignore** back. A game that
quits when you press back — most of them — got there first, and looked completely normal.

### "Are you sure you want to quit?" now quits

With back working again, **Cut the Rope**'s quit confirmation appeared — and answering **Yes** did
nothing at all.

Windows Phone never gave games a way to close themselves. What it gave them was a loophole, and
essentially every game that offers a quit option uses it: the game deliberately fails, in a way it
recognises, and the phone shuts it down. WPR was catching the failure and carrying on, so the game
politely asked to be closed and was politely ignored.

WPR now completes the loophole, and only for a game that is clearly using it on purpose. A game
that merely runs into a problem is still kept running rather than closed — that is what keeps a
game with a small fault playable instead of dying at the first hiccup.

### Funny Bounce closed itself on Android, for a second reason

Separate from the blue screen further down, and only visible once that was fixed: the game reached
its menu and then closed.

It shows an advert banner, and the picture for that banner arrives over the internet rather than
from a file. WPR's picture reader assumed every picture could be skipped through freely, the way a
file can — a download cannot; it only arrives in order. Asking it to skip backwards failed, and
because that failure happened deep inside the picture reader it took the game with it.

The picture reader now copes with pictures that arrive a piece at a time, and stops any failure
there from reaching the game. **Any game showing an advert banner** was exposed to this.

### The Treasures of Montezuma, on Android this time

It plays on Windows from the fix further down. On Android it still closed immediately, with a
complaint about a duplicated name.

The same copy protection, one layer deeper. As well as checking that its own parts had not been
renumbered, the game checks **who is calling** when it unscrambles a piece of text — and on
Android's new engine that check was coming back wrong. The game's response to a failed check is
not to stop; it is to hand out the *same wrong word* for every piece of text it is asked for. The
duplicate name was two different things that had both come back as the same nonsense.

WPR now satisfies that check, so the text unscrambles and the game plays on the phone as it does
on Windows. Only this game and **Farm Frenzy 2** are protected this way, so nothing else in the
library is affected either way.

### Adding games to the phone had quietly stopped working

Not visible as an error — that is the point of mentioning it.

To install a game, WPR rewrites it, and to rewrite it WPR needs one of its own files sitting on
the phone's storage as a real file. The new .NET engine packs those files away differently, so
WPR could no longer find the one it needed. Installing appeared to succeed and the game would
start, but part of the rewriting had been skipped.

WPR now ships that file plainly rather than digging it back out, which no future change to how
.NET packs things can break. If you installed or updated a game on the phone since the engine
changed, it is worth repatching it.

### Plants vs. Zombies froze on the PopCap logo — on Android only

The logo appeared and stayed there. No error, no crash, and the phone was not even busy: the game
had simply stopped. On Windows it played normally.

Plants vs. Zombies loads while it shows the logo, and it does that loading in the background while
the front of the game keeps drawing. Both halves draw pictures, and the game keeps them from
getting in each other's way with a lock of its own. The graphics driver Android uses also has a
lock, and it held on to it not just while it was drawing but for as long as a whole batch of
drawing stayed open — which, between two halves of the same game, can be a long time. So each half
ended up holding one lock and waiting for the other, and neither could ever go on.

The driver now holds its lock only while it is actually doing something, and if one part of a game
needs the graphics card while another part has left a batch open, it closes that batch instead of
waiting. Nothing is lost by doing so. **Any game that draws from two places at once was exposed to
this**, not just this one — Plants vs. Zombies was simply the one that hit it every time.

Windows never had the problem, because its default graphics mode was never built that way. It
plays the same as before: logo, title screen, menu, and into the levels.

Switching the phone to the older graphics mode is **not** a workaround for this game — it stops
even earlier there, for a separate, long-known reason in that mode.

### Links in games open now

Until now, a link in a game did nothing at all. Windows Phone games use them more than you would
think: **Cut the Rope**'s entire **Cartoons** section is links — every episode opens YouTube, which
is how it worked on the phone — and games routinely have "more games", "rate us" and website
buttons. Tapping any of them did nothing, and in Cut the Rope's case the episode still got marked
as watched.

Links now open. On **Windows** they go to your default browser. On **Android** the phone decides,
the same way it does for a link anywhere else, so a YouTube link opens in the YouTube app if you
have it. Cut the Rope's cartoons use an old YouTube address format that only the Windows Phone
YouTube app understood; WPR turns it into an ordinary YouTube link first.

Only web links are opened. What a game asks to open is up to the game, and a 2011 phone game has
no reason to open anything else on your computer or phone, so anything that is not a web address
is ignored and noted in the log.

**Share buttons work on Android** too, and bring up the phone's normal share menu with the game's
text and link filled in — Cut the Rope's Share button, on the screen after a cartoon, is the one to
try. On **Windows** a share button still does nothing; that needs the Windows share panel, which is
its own piece of work.

Only the first cartoon episode is there to watch. The rest came from an online list that no longer
exists; the first one is built into the game.

Neither of these needs a repatch or a reinstall.
