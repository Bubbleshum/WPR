# WPR 0.2.03: full release notes

The long version: what each change actually is, how it behaves, and what's still missing. The
short summary that goes on the release page is [`0.2.03.md`](0.2.03.md) beside this file.

---

**Gravity Guy and iStunt 2 start on Windows again, AE 3D Motor and Skulls of the Shogun play, and Android games that crashed or showed a black screen on Mali phones and on OpenGL draw again.**

> **Switched to OpenGL to get around a crash?** If you changed settings → graphics to OpenGL because
> games crashed on Vulkan, switch it back to Vulkan after updating. Your own choice always wins over

### Windows games that couldn't find Microsoft.Phone

Both games died before their first frame on the Windows release, with a `FileNotFoundException`
for `Microsoft.Phone, Version=7.0.0.0` out of Miniclip's shared Cocos2D library. The same games ran
fine in a development build, which is what pointed at the release itself.

**What it was.** WPR ships its own versions of three Windows Phone libraries, and their version
numbers are part of their identity: `Microsoft.Phone` and `Microsoft.Devices.Sensors` are 8.0.0.0,
`System.Device` is 2.0.5.0. The release workflow set the product version with `-p:Version=…` on the
command line, and a command-line property overrides every project's own setting, those three
included. So the 0.2.02 installer shipped all three as **0.2.2.0**. .NET only loads a library whose
version is at least the one asked for, and 0.2.2.0 is lower than both 7.0.0.0 (what WP7 games ask
for) and 8.0.0.0 (what WP8 games ask for). The game's request failed and the launch stopped.

This had been in the release workflow since it was first written, so it was never specific to
Miniclip's games. Any WP7 or WP8 game on the Windows release that touched one of those libraries
could fail the same way. Gravity Guy and iStunt 2 were the ones reported.

**The fix.** The release now sets the version through `WprVersion`, which only the two app projects
read, so the phone libraries keep their own numbers. Checked against what games actually ask for:
across every installed game and the 104 WP8 XAPs in the test library, no game asks for a higher
version than WPR now ships.

**Not affected:** Android, whose build never set `Version`, and development builds from Rider or
`build-desktop.ps1`.

### Mali phones and Vulkan

Reported on a realme RMX3938 (Android 16) with Bejeweled Live+ (#51), and earlier on a Samsung
Galaxy A30s (Android 11, Mali-G71) with Funny Bounce (#41): every game crashed on Vulkan before its
first frame with `vkCreateDevice VK_ERROR_FEATURE_NOT_PRESENT`.

**The Vulkan crash.** FNA3D's Vulkan driver turned on three optional device features
(`occlusionQueryPrecise`, `fillModeNonSolid`, `samplerAnisotropy`) without asking the device whether
it had them. Asking for a feature the device lacks makes `vkCreateDevice` fail, and Mali chips
commonly report no `fillModeNonSolid` (wireframe drawing). It was never specific to one game: no
game could create a Vulkan device on such a phone. The driver now queries the device and enables
only what it reports. Without wireframe support a wireframe draw is drawn solid; without anisotropy
a sampler keeps its linear filtering; without precise occlusion queries the query runs imprecise.
Anything missing is logged once as `Vulkan device lacks optional features: …`.

**The crash every other launch.** WPR's crash breadcrumb did switch the phone to OpenGL after the
Vulkan crash, but only remembered the last launch. The OpenGL launch then wrote "worked" over the
record, and the launch after that tried Vulkan again. A driver that never reaches its first frame is
now remembered as one to avoid until it works again, until you pick a driver under settings →
graphics, or until a system update or a new version of WPR, either of which may have fixed it.

A driver picked by hand in settings still outranks all of this, which is why anyone who switched to
OpenGL to get around the crash has to switch back to benefit.

### Black screens on OpenGL

OpenGL is where a phone ends up when its Vulkan driver fails, so these matter most on exactly the
phones above. Both were found on the emulator, forced to OpenGL.

**Games that load in the background.** Bejeweled Live+ loads its art on a background thread while
holding a lock its game loop also waits for. FNA3D's OpenGL driver used to make a background
thread's texture wait in a queue until the next frame was shown, and the next frame never came,
because the game loop was waiting on that lock. Reproduced on the desktop on every OpenGL variant
(desktop GL, GLES3, GLES3 without DXT), while Vulkan loads all 405 assets and plays.

Fixed on Android by giving background threads OpenGL contexts of their own, shared with the game's:
a background texture or buffer upload borrows one of two pooled contexts, runs there, finishes, and
hands it back, with no frame involved. Effects, readbacks and render buffers still use the queue. If
the phone can't do this, WPR logs it and goes back to the queue. On the emulator, Bejeweled Live+
goes from a black screen to its menu and a playable game; with the pool switched off, the same build
is black again.

**Drivers that claim more than they have.** FNA3D decides whether an optional GL function exists by
whether its entry point loads. On OpenGL ES that proves nothing: Android's `eglGetProcAddress` can
return a stub for a function the driver doesn't implement, and the emulator's stub prints
`called unimplemented OpenGL ES API` and does nothing. So on an ES 3.1 driver FNA3D believed it had
ES 3.2's base-vertex draws (`glDrawRangeElementsBaseVertex`), and every indexed draw with a base
vertex drew nothing: Archer was black, The Treasures of Montezuma showed only its clear colour. FNA3D
has always had a fallback for drivers without base-vertex draws (it offsets the vertex attributes
instead); it just never chose it.

On ES, base-vertex draws now need ES 3.2 or the `GL_OES_draw_elements_base_vertex` /
`GL_EXT_draw_elements_base_vertex` extension, and the desktop-only functions (`glPolygonMode`,
`glGetTexImage`, `glGetBufferSubData`) are never considered present. On the emulator (OpenGL ES 3.1)
Archer reaches its title screen and Montezuma its main menu, the stub message is gone, and Bejeweled
Live+ still plays.

**Not built for Windows.** Both OpenGL changes are in the Android build of FNA3D only; the Windows
`FNA3D.dll` can't be rebuilt here, and the desktop uses D3D11 anyway.

### AE 3D Motor

The game showed a white screen and never got further. Two things were wrong, and fixing the first
uncovered the second.

**The white screen.** WPR raises Windows Phone's "app resumed" signal (`Activated`) once at every
start, because several games only set themselves up when they see it. AE 3D Motor reads it the way
the phone meant it: as a return from being suspended. It cleared its screens, then tried to read
back the state it saves when suspended, which doesn't exist on a first start, and stopped there with
nothing on screen. The game is now on WPR's short list of titles that don't get that signal at start
(with Doodle God and Chickens Can't Fly); it still gets it on a genuine resume.

**The crash behind it.** With its splash screen now drawn, the game crashed outright in the graphics
driver. It creates its graphics device in its constructor, and starting the game loop replaces that
device with the real one, as XNA always did. But WPR raised the "app launched" signal (`Launching`)
*before* starting the loop, so the splash screen loaded its pictures onto the device about to be
thrown away, and the first draw read freed memory. On the phone, `Launching` only ever came once the
game was running. Now, for a game that already has a device when WPR is about to start it, WPR skips
that early `Launching` and the game gets it once, after its first frame, on the device it keeps.

Five installed games create their device that early: AE 3D Motor, ilomilo, Mirror's Edge, Skulls of
the Shogun and Tower Bloxx New York. Only ilomilo and Skulls listen for these signals, and neither
does anything at start that the change affects; all of them still run.

Played on Windows on D3D11, Vulkan and OpenGL, and on the Android emulator on Vulkan and OpenGL ES
3.1: menu, a race steered by tilt, and game over. Not yet run on a phone.

### Skulls of the Shogun

The game closed while loading its world map. Its map file stores the names of the types it contains,
one of them a list of XNA `Vector2`s, written as a type name with another full type name nested
inside it. WPR's version of `Type.GetType`, which every game's calls are redirected to, cut type
names apart at each comma, so it mangled the nested one into an invalid name
(`'FNA,  mscorlib'`) and the load threw on the game's loading thread.

It also pointed every XNA type name at the `FNA` library, which no longer contains any XNA types.
`Type.GetType` now leaves the parsing to .NET's own type-name parser and only tells it where each
library is: XNA names go to WPR's XNA library, game libraries are looked up next to the game asking
first, then everywhere else, as before.

Skulls of the Shogun now loads the map and plays into a battle on Windows. The seven other installed
games that use `Type.GetType` this way were re-run and still start: Pitfall!, Feed Me Oil, Dream
Track Nation, Chickens Can't Fly, Carcassonne and two Silverlight titles, one of which (What In The
World?) the test harness can't run, so it was not checked. Not yet run on Android, where the same
code is used.

### Not verified on a phone

Everything above on Android was tested on the emulator. None of it has run on a Mali phone yet: the
Vulkan fallbacks were never exercised on a device that lacks those features.

Archer's reporter (#62) has a Galaxy A30s, whose Mali-G71 is an OpenGL ES 3.2 GPU. It really has
base-vertex draws, so the ES 3.1 fix may not be what fixes Archer there. The Vulkan fix should let
that phone use Vulkan again, where Archer works on the emulator and the desktop. A logging run from
it on 0.2.03 would settle it.

### Known issues

- **Galactic Reign** sometimes closes while loading on Android (seen in about 2 of 9 launches on the
  emulator, on Vulkan and OpenGL alike). It's a stack overflow in the game's own navigation code,
  which re-posts itself through WPR's Silverlight dispatcher, and that dispatcher runs work at once
  instead of queueing it. Not a graphics problem; being fixed separately.

> **Upgrading is normal.** Install the new APK over the top on Android, or run the installer on
> Windows. Your games, saves and sign-in stay put. Nothing needs repatching or reinstalling.
