### Windows games that couldn't find Microsoft.Phone

Both games died before their first frame on the Windows release, with a `FileNotFoundException`
for `Microsoft.Phone, Version=7.0.0.0` out of Miniclip's shared Cocos2D library. The same games ran
fine in a development build, which is what pointed at the release itself.

**What it was.** WPR ships its own versions of three Windows Phone libraries, and their version
numbers are part of their identity: `Microsoft.Phone` and `Microsoft.Devices.Sensors` are 8.0.0.0,
`System.Device` is 2.0.5.0. The release workflow set the product version with `-p:Version=…` on the
command line, and a command-line property overrides every project's own setting, those three
included. So the 0.2.02 installer shipped all three as **0.2.2.0**. .NET only loads a library whose
version is at least the one asked for, and 0.2.2.0 is lower than both 7.0.0.0 (what WP7 games ask
for) and 8.0.0.0 (what WP8 games ask for). The game's request failed and the launch stopped.

This had been in the release workflow since it was first written, so it was never specific to
Miniclip's games. Any WP7 or WP8 game on the Windows release that touched one of those libraries
could fail the same way. Gravity Guy and iStunt 2 were the ones reported.

**The fix.** The release now sets the version through `WprVersion`, which only the two app projects
read, so the phone libraries keep their own numbers. Checked against what games actually ask for:
across every installed game and the 104 WP8 XAPs in the test library, no game asks for a higher
version than WPR now ships.

**Not affected:** Android, whose build never set `Version`, and development builds from Rider or
`build-desktop.ps1`.

> **Upgrading is normal.** Install the new APK over the top on Android, or run the installer on
> Windows. Your games, saves and sign-in stay put. Nothing needs repatching or reinstalling.
