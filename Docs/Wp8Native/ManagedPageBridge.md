# Running a Direct3D/XAML title's own managed page

Status: design + trial (branch `xna-facades`, 2026-10-26). Trial title: Amazing Alex
(`fac2552c-25bb-420c-b0b5-bb3059418933`).

## The problem

A WP8 Direct3D/XAML title is two halves: a native WinRT component (the game, ARM C++/CX:
`AlexXamlComponent.dll` + `FusionComponent.winmd`) and a managed Silverlight shell (`AmazingAlex.dll`:
`App`, `MainPage`) that activates the component, sets it up, hands its content provider to a
`DrawingSurfaceBackgroundGrid`, and forwards lifecycle, Back, orientation and text input to it.

Today WPR does not run the shell. It **imitates** it: `XamlShells.cs` (hand-written step lists for
three titles), `XamlShellInference*.cs` (reads the shell's IL and guesses the calls for the rest) and
`MandreelMessages.cs` (plays Mandreel's managed thread). Every new title is a new guess, and the
guesses are where the defects came from (a view size answered by parameter name; a timer handler not
followed; a message thread never started). That is the "imitate a shipped library" pattern
`.claude/rules/never-shim-bundled-dlls.md` forbids, applied to the game's own code.

## The design

Run the shell as shipped, on the Silverlight host, and make its WinRT calls reach the native
component.

```
AmazingAlex.dll (as shipped, patched like any WP8 managed title)
   new FusionMain(), fusionMain.WindowBounds = ..., CreateContentProvider(), add_OpenInput(...)
        |
FusionComponent.dll  -- generated by WinmdStubber in "bridged" mode: the winmd's exact types,
        |               whose bodies call WinRtComponentBridge instead of returning default
        |
WPR.WinRT.WinRtComponentBridge (WPR.Framework.WinRT)  -- the slot; speaks object[] and names
        |
WPR.Wp8Native ComponentBridge (the WP8 runtime)  -- queues the call to the guest thread, marshals
        |                                           by the winmd (WinmdReader), calls the vtable slot,
        |                                           blocks the caller until the guest returns
AlexXamlComponent.dll (as shipped, ARM, on dynarmic)
```

and the reverse direction:

```
DrawingSurfaceBackgroundGrid.SetBackgroundContentProvider(proxy)  -> ContentProviderSet hook
   -> the runtime takes the proxy's guest pointer and Connects it, as XamlInterop does today
   -> frames: an IEmbeddedGameLoop under SilverlightGame (the SharpDX path's shape)
component raises OpenInput("...")  -> a guest-callable delegate object whose Invoke unmarshals the
   arguments and invokes the managed delegate the page subscribed
```

### Pieces

1. **Bridged stubs** (`WinmdStubber`, install time). Same type layout as today's stubs. Bodies:
   - runtime class constructor: `__handle = WinRtComponentBridge.Activate("NS.Class", args)`;
   - instance method/property: `WinRtComponentBridge.Invoke(this, "NS.Class", "name", args)`,
     result unboxed or wrapped;
   - static: same with a null target;
   - event add/remove: `Invoke` with the delegate as the argument, `EventRegistrationToken` back;
   - a result that is a runtime class or an interface comes back as a guest pointer and is wrapped
     by the stub in its own type (an internal pointer constructor) or a generated proxy class
     implementing the interface, so casts in game IL hold.
   Every generated object implements `IWinRtGuestObject { long GuestPointer; }`.
2. **`WinRtComponentBridge`** (`WPR.Framework.WinRT`, assembly `System.Runtime.WindowsRuntime`, which
   the stub already references). One registered implementation per launch; null means "no runtime",
   and the calls answer defaults (today's stub behaviour).
3. **The runtime side** (`WPR.Engine.Wp8Native`). `WinRtRuntime.InvokeMember` already calls a member
   by name with metadata marshalling, and `XamlCallback` already makes guest-callable delegates; the
   bridge reuses both. New: a request queue serviced on the guest thread (before the provider is
   set: an idle loop; after: once a frame in `NextFrame`), and a blocking wait on the caller.
4. **Hosting** (`ApplicationLaunch`, `SilverlightGame`). The title runs on `SilverlightGame` like any
   WP8 managed title. The WP8 runtime is started for its component (DllMain, the activation factory)
   and drawn as an `IEmbeddedGameLoop` under the page. `Wp8NativeGame`'s frame, input and drawing code
   moves into a session class both the stand-alone `Game` (exe titles) and the embedded loop use.
   Lifecycle, Back and orientation then come from the page itself, through the bridge.

### What goes away

`XamlShells.cs`, `XamlShellInference*.cs`, `MandreelMessages.cs` (~1,800 lines), `XamlShell`'s
step playback in `XamlInterop.cs`, and the per-title knowledge in all of them. A new Direct3D/XAML
title needs nothing written for it.

### Threading

- Managed page code runs on the game thread. A bridge call posts to the guest thread and waits.
- The guest calls managed delegates **on the guest thread**, synchronously, as WinRT does on its
  thread. Shells marshal to the UI thread themselves (`Dispatcher.BeginInvoke`), which WPR queues.
- A managed delegate that calls back into the component **while on the guest thread** cannot wait
  for the guest. Trial: refused and logged (`[wpr-bridge] re-entrant call`). Full: run it as a
  nested guest call (the runtime is continuation-passing, so this needs a nested run loop).

### Risks

- Marshalling coverage: the runtime's `Marshal` knows float/int/bool/string/Size/host objects. Each
  new type a shell passes is a new case (but a general one, shared by every title).
- `WinmdStubber` in bridged mode must keep the native DLL and the `.winmd` where the runtime finds
  them (it moves both aside today).
- Exe titles must not regress: the session extraction from `Wp8NativeGame` is the risky edit; the
  WP8 regression set (11 titles) and the contract tests cover it.

## Trial result (2026-10-26, desktop D3D11, harness)

Opt-in: `WPR_WP8_MANAGED_PAGE=1`, on an install readied with `gamerun --prepare-page <folder>`
(bridged `WinmdStubber`, `WindowsTypeSynthesizer`, the patcher). Amazing Alex's own `App` and
`MainPage` ran on `SilverlightGame`; the component ran on the WP8 runtime as the embedded loop.

- **The page's own calls reached the component**, in its own order: `new FusionMain()`,
  `add_OpenInput/CloseInput/SendEmail` (tokens 1, 2, 3 back), `WindowBounds` 480x800,
  `NativeResolution` 768x1280, **`get_NativeResolution`** (the page reads it back to set
  `RenderResolution` - the hand-written description could not do that), `m_TextInputContent`,
  `ScaleFactor` 160, `Orientation` 1, `CreateContentProvider`, the provider connected through the
  grid's hook, `SetManipulationHost` through the grid's other hook, `m_enableMusic`.
- **Frames**: loading screen, then the main menu, 59.5 fps, the same screens as the hand-written run.
- **Back**: the page's `BackKeyPress` asked `IsSafeToQuit()` (1 on the menu), let Back through, and
  `Application_Closing` called `Dispose()` -> `IClosable::Close` on the component.
- **Input**: a tap at (400,250) on the 800x480 page reached the component's own pointer handlers at
  (640,400) in its 1280x768 frame. A harness tap on Play leaves BOTH paths on the menu; not chased.
- Defects found and fixed on the way, general ones: `WinmdStubber` gave delegate types IL bodies (a
  `new OpenInput(handler)` did nothing); it did not apply the WinRT projection's rename of
  `Windows.Foundation.EventRegistrationToken` (the page's `add_` calls did not bind) or of
  `IClosable` to `IDisposable` (the page calls `Dispose`).

Regression of the `Wp8NativeGame` -> `Wp8NativeSession` extraction (flag off): 7 WP8 titles (Angry
Birds Rio, Angry Birds, Stella, MC4, AC Pirates, Fruit Ninja, Amazing Alex), old vs new build, 30 s
each: same exits, nothing thrown, frame counts within noise, same screens (differences were animation
phase). WP8 contract tests 2336 pass; the 3 failures are the unlock-toast checks that already fail on
0.2.07.

### Left for the real thing

- Make it the default for every Direct3D/XAML title with a managed shell, at install (bridged stubs +
  the synthesizer + the patcher), and delete `XamlShells.cs`, `XamlShellInference*.cs`,
  `MandreelMessages.cs`.
- Calls on guest objects other than the page's first instance (a second runtime class, an interface
  the component returns): the runtime's member lookup is per-instance today.
- A C# handler calling back into the component while the guest is raising it (refused now).
- `DrawingSurface` (not background-grid) titles: the Mandreel and Gameloft WCP family.
- Android, D2-D4, a phone.

## Trial plan (Amazing Alex, desktop D3D11)
